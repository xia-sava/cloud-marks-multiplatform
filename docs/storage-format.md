# S3 上の形式

Cloud Marks のデータは、S3 の 1 つのプレフィックスの下に置く。Android・デスクトップ・Native Messaging のホストは、
対等にこれを読み書きする。中継するサーバーは置かない。

対象とするストレージは、AWS の S3 と、PutObject の `If-Match` / `If-None-Match` に対応する S3 互換のストレージに限る。

## 構成

データは、フォルダのツリーを持つ**マニフェスト**と、フォルダごとの項目を持つ**項目ファイル**からなる。

```text
<プレフィックス>/
├─ manifest.jsonl.gz                          マニフェスト
└─ folders/<フォルダの ID>/<ファイルの ID>.jsonl.gz   項目ファイル
```

- 書き換えるオブジェクトはマニフェストだけ。項目ファイルは一度置いたら書き換えない。フォルダの中身が変わるときは、
  新しいファイルの ID で別のオブジェクトとして置き、マニフェストが指すファイルを新しく置いたものに替える
- マニフェストの書き換えは条件付き書き込み（`If-Match`）で行う。マニフェストの中身が、そのままデータ全体の状態になる。
  いくつのフォルダにまたがる変更も、マニフェストの書き換え 1 回で一度に反映される
- バケットとプレフィックスは利用者が設定で与える。プレフィックスは前後の `/` を除いて扱い、キーは
  `<プレフィックス>/manifest.jsonl.gz` のように `/` でつなぐ。プレフィックスが空なら、キーはプレフィックスと `/` を付けずに始まる（`manifest.jsonl.gz`、`folders/…`）

## 共通の決まり

- **JSONL。** 1 行に 1 つの JSON オブジェクトを書き、各行を LF で終える。最後の行も LF で終える。空の行は置かない。
  文字コードは BOM の無い UTF-8
- **1 行目はヘッダー。** 2 行目から中身が続く
- **gzip で圧縮して置く。** キーの末尾は `.jsonl.gz`、`Content-Type` は `application/gzip`。
  `Content-Encoding` は付けず、読み手が自分で展開する。付けると HTTP の層が自動で展開し、受け取る中身が、圧縮したものを指す長さや ETag と合わなくなる
- **ID は乱数の UUID（バージョン 4）。** RFC 9562 の小文字・ハイフン区切りの 36 文字（例：`0b9a6c1e-3f2d-4e5a-9b7c-1d2e3f4a5b6c`）。
  フォルダ・項目・項目ファイル・書き込みのそれぞれに振る。比べるときは文字列として比べる。
  ID はキーの一部になるため、この形（小文字の 16 進で 8-4-4-4-12）に合わない値は壊れているとみなす。読み手はバージョンの桁を確かめない
- **日時は RFC 3339 の UTC。** 書き手は末尾を `Z` にし、小数部をちょうど 3 桁で書く（例：`2026-11-16T12:34:56.789Z`）。
  ミリ秒未満は切り捨てる。読み手は小数部の桁数によらず受け入れる
- **ETag は不透明な値として扱う。** 応答の値を引用符ごとそのまま覚えて条件に渡し、中身を解釈しない。
  暗号化の設定によっては、ETag は中身の MD5 ではない

## 形式のバージョン

形式のバージョンはマニフェストのヘッダーだけが持ち、データ全体に当てはまる。項目ファイルの形を変えるときも、マニフェストの形式のバージョンを上げる。

- `version`：データを書いた形式のバージョン
- `readableBy`：このデータを読むのに要る最低のバージョン。`version` 以下

クライアントは、自分の知っているバージョンを N として次のように振る舞う。

| マニフェストのヘッダー | 振る舞い |
|---|---|
| `readableBy` > N | 読まない。「アプリの更新が要る」と伝える |
| `readableBy` ≤ N < `version` | 読むだけにして、書かない。古いファイルの削除もしない。「アプリの更新が要る」と伝える |
| `version` ≤ N | 読み書きする |

- 書き手は、読んだマニフェストの `version` のまま書く。そのバージョンで表せない内容を書くときだけ `version` を上げる。
  以前の状態に戻すときは、戻す時点のマニフェストの `version` と `readableBy` を書く（「以前の状態に戻す」）
- 欄を足すときは、古いクライアントが知らない欄を落として書き戻さないよう、必ず `version` を上げる。
  古いクライアントが無視して読んでも誤らない欄なら `readableBy` は据え置き、誤るなら `readableBy` も上げる
- 新しいバージョンで表す機能は、すべてのクライアントがそのバージョンを読めるようになってから使い始める
- 読み手は、自分の知っているバージョン以下のすべてのバージョンを読める
- 読み手はヘッダーを `format`、`version` と `readableBy`、残りの欄の順に確かめる。形式のバージョンが自分の知っているバージョンより新しいときに
  ほかの検証で失敗したら、「壊れている」ではなく「アプリの更新が要る」と伝える
- 書き手は、ここに定めた欄だけを書く。読み手は、知らない欄があっても無視して読む

## マニフェスト

キーは `<プレフィックス>/manifest.jsonl.gz`。

### ヘッダー（1 行目）

```json
{"format":"cloud-marks-manifest","version":1,"readableBy":1,"commit":"<UUID>","updatedAt":"2026-11-16T12:34:56.789Z","updatedBy":"desktop"}
```

| 欄 | 型 | 内容 |
|---|---|---|
| `format` | 文字列 | `"cloud-marks-manifest"` |
| `version` | 整数 | 形式のバージョン。1 以上 |
| `readableBy` | 整数 | 読むのに要る最低のバージョン。1 以上で `version` 以下 |
| `commit` | 文字列 | 書き込みごとに新しく振る UUID。自分の書き込みが成功していたかを確かめるのに使う（「書き込みの手順」） |
| `updatedAt` | 文字列 | 書き込んだ日時 |
| `updatedBy` | 文字列 | 書き込んだクライアントの種類。`"android"`・`"desktop"`・`"host"` など。後から追うための記録で、読み手は知らない値も受け入れ、この値で振る舞いを変えない |

### フォルダ（2 行目から）

1 行に 1 フォルダ。**2 行目は必ずルートフォルダ**で、`parent` が null なのはこの行だけ。ルートフォルダは名前が空で、画面には名前を出さない。
ルートフォルダもほかのフォルダと同じく、子のフォルダと項目を持てる。

```json
{"id":"<フォルダの ID>","parent":"<親のフォルダの ID>","name":"資料","items":"<ファイルの ID>","count":3}
```

| 欄 | 型 | 内容 |
|---|---|---|
| `id` | 文字列 | フォルダの ID |
| `parent` | 文字列か null | 親のフォルダの ID。ルートフォルダだけが null |
| `name` | 文字列 | フォルダの名前。ルートフォルダは空、それ以外は空でない。`/` を含め、どの文字でも使える。兄弟で同じ名前があってもよい |
| `items` | 文字列か null | このフォルダの項目を持つ項目ファイルの ID。項目が無ければ null |
| `count` | 整数 | 項目の数。0 以上。項目が無ければ 0 |

- **並びは、ルートフォルダから深さ優先の行きがけ順。** 親は必ず子より前の行に出てくる。兄弟どうしの並び順は、そのまま行の順になる
- フォルダは、子のフォルダと項目の両方を持てる。表示の並びは、子のフォルダが先で項目が後。
  子のフォルダの並びはマニフェストが、項目の並びは項目ファイルが持つ
- `items` が null であることと `count` が 0 であることは、必ず揃う。書き手は、項目の無い項目ファイルを置かない

### 読み手が確かめること

次のどれかを満たさないマニフェストは壊れているとみなす。読み手は失敗として利用者に伝え、書き込みも古いファイルの削除もしない。
壊れたマニフェストは、バケットのバージョニングで残っている古いバージョンから手で戻す（「以前の状態に戻す」）。

- gzip として展開でき、BOM の無い UTF-8 として読め、すべての行が JSON のオブジェクトとして読める。空の行が無く、最後の行が LF で終わる
- 1 行目がヘッダーで、`format` が `"cloud-marks-manifest"` である。ヘッダーとフォルダの各行が、表の欄をすべて表の型で持つ。
  null を許す欄も、欄ごと省けない。整数は JSON の整数の字句で書かれている。日時は RFC 3339 の日時として読める
- `version` と `readableBy` が 1 以上の整数で、`readableBy` が `version` 以下である
- `commit`・`id`・`parent`・`items` の値が、null を許すものを除いて UUID の形である
- `id` が重複しない
- 2 行目があり、その `parent` が null で `name` が空である（ルートフォルダ）
- 3 行目からの各行の `parent` が、**直前の行から `parent` を辿ってルートフォルダへ向かう途中にあるフォルダ**（直前の行そのものを含む）の `id` である。
  これで、親が先にあること、循環が無いこと、行きがけ順であることを 1 回の走査で確かめられる
- 3 行目からの各行の `name` が空でない。`count` が 0 以上の整数である
- `items` が null であることと `count` が 0 であることが揃っている

## 項目ファイル

キーは `<プレフィックス>/folders/<フォルダの ID>/<ファイルの ID>.jsonl.gz`。

### ヘッダー（1 行目）

```json
{"format":"cloud-marks-items","folder":"<フォルダの ID>"}
```

| 欄 | 型 | 内容 |
|---|---|---|
| `format` | 文字列 | `"cloud-marks-items"` |
| `folder` | 文字列 | このファイルを持つフォルダの ID。キーのフォルダの ID と同じ |

形式のバージョンはマニフェストのヘッダーが持つため、項目ファイルは持たない。

### 項目（2 行目から）

1 行に 1 項目。行の順が表示の並び順になる。

```json
{"id":"<項目の ID>","url":"https://example.com/","title":"Example","added":"2026-11-16T12:34:56.789Z"}
```

| 欄 | 型 | 内容 |
|---|---|---|
| `id` | 文字列 | 項目の ID。すべてのフォルダを通して重複しない |
| `url` | 文字列 | 空でない。スキームは問わない（`https`・`http` のほか `about:` や `moz-extension:` もありうる） |
| `title` | 文字列 | 空でもよい |
| `added` | 文字列 | 省略可。追加した日時。既存の cloud-marks から取り込んだ項目には無い |

- 同じ URL の項目が複数あってもよい
- 既読かどうかは持たない。フォルダに残っている項目が未読で、読み終えた項目は利用者が消す

### 読み手が確かめること

次のどれかを満たさないファイルは壊れているとみなす。

- gzip として展開でき、BOM の無い UTF-8 として読め、すべての行が JSON のオブジェクトとして読める。空の行が無く、最後の行が LF で終わる
- ヘッダーと項目の各行が、表の欄を表の型で持つ。`added` は省略でき、持つなら RFC 3339 の日時として読める
- 1 行目がヘッダーで、`format` が `"cloud-marks-items"` である
- `folder` が、キーのフォルダの ID とも、このファイルを指しているマニフェストのフォルダの `id` とも一致する
- 項目の行の数が、マニフェストのそのフォルダの `count` と一致する
- `id` が UUID の形で、ファイルの中で重複しない。`url` が空でない

壊れたファイルを持つフォルダについては、その中身を変える操作を止め、利用者に伝える。そのフォルダごとの削除や、
ほかのフォルダへの操作はできる。

## 書き込みの手順

すべての変更は、次の手順を 1 回の書き込みとして行う。

1. マニフェストを読む。ローカルキャッシュにマニフェストと ETag があれば `If-None-Match: <ETag>` を付けて GET し、
   `304` ならローカルキャッシュのものを使う。`200` と `304` 以外は失敗として利用者に伝える（「マニフェストを新しく作る」）。
   読んだマニフェストは検証し、形式のバージョンを確かめる（「形式のバージョン」）
2. 操作を、読んだ状態に適用する。適用した結果が読んだ状態と同じなら、ここで終える（PUT しない）
3. 中身の変わったフォルダごとに、新しいファイルの ID で項目ファイルを PUT する。`If-None-Match: *` を付ける。
   項目が無くなったフォルダはファイルを置かず、`items` を null にする。
   複数のファイルは並行して送ってよい。すべて成功してから手順 4 へ進む
4. マニフェストのヘッダーの `commit` に新しい UUID を振り、`If-Match: <手順 1 の ETag>` を付けてマニフェストを PUT する。
   **手順 3 の最初の PUT から 1 時間を過ぎていたら、手順 4 の PUT を送らずに手順 1 からやり直す**（ファイルも新しい ID で置き直す）。
   経過は端末のモノトニッククロックで測る
5. 応答に応じて次のようにする

### 応答ごとの扱い

手順 4（マニフェストの PUT）：

| 応答 | 扱い |
|---|---|
| `200` | 成功。応答の ETag と書いたマニフェストをローカルキャッシュに持つ |
| `412` | 読み直して、「成功の判定」をする。成功していなければ、手順 1 から操作を再適用する |
| `409` | 同時に走った書き込みとの衝突。同じ PUT を再送する |
| `404` | マニフェストが消されている。失敗として利用者に伝え、書き込みを止める |
| 結果が不明（タイムアウト、接続の切断、`5xx`、`503 SlowDown`） | 読み直して、「成功の判定」をする。成功していなければ、手順 1 から操作を再適用する |
| `403` など、上のどれでもないもの | 失敗として利用者に伝え、再適用しない |

手順 3（項目ファイルの PUT）：

| 応答 | 扱い |
|---|---|
| `200` | 成功 |
| `409` または結果が不明 | 同じ PUT を再送する |
| `412` | 再送したあとなら、先の PUT が成功していた。最初の PUT で返ったなら、ファイルの ID を振り直して置き直す |
| `403` など、上のどれでもないもの | 失敗として利用者に伝え、再適用しない |

- 再送と再適用は、間を空けて行い、回数に上限を設ける。上限を超えたら失敗として利用者に伝える
- 手順 4 の PUT を一度でも送ったあとのマニフェストの GET（成功の判定のための読み直し、再適用の手順 1）は、
  結果が不明のときに再送する。手順 4 より前の GET は再送しない

### 成功の判定

自分のマニフェストの PUT は、応答が途中で切れた、遅れて届いた、SDK が自動で再送して `412` を受けた、などのときに、
応答を受け取れないまま成功していることがある。このまま操作を再適用すると、追加のような操作では項目が二重になる。
これを次の二つで防ぐ。

- **1 回の操作のあいだに手順 4 で振った `commit` をすべて覚えておく。** 読み直したマニフェストの `commit` がそのどれかなら、
  書き込みは成功していた
- **操作が作るもの（フォルダ・項目）の ID は、操作を組み立てるときに一度だけ振り、再適用するときに振り直さない。**
  再適用するとき、その ID が既にあれば、その部分は適用済みとして扱う。自分の書き込みのあとに別の端末の書き込みが挟まって
  `commit` が替わっていても、これで二重にならない

`412` を受けた、または結果が不明だった手順 4 の PUT は、届いたかどうかが分からないものとして記録する。読み直したマニフェストの
`commit` が自分の振ったものでなく、ETag がその PUT の `If-Match` と違えば、その PUT はもう届かないとして記録を消す。

読み直しが上限まで失敗したときのように、記録が残ったまま書き込みを終えるときは、ただの失敗ではなく
**確かめられなかった**として返す。書き換えが済んでいることもある。呼び出し側が同じ操作（同じ ID）でもう一度
書き込めば、届いていた分は適用済みになり、二重にならない。やり直した書き込みが成功以外で終わっても、確かめられないままとして扱う。
やり直しの失敗は、先の PUT が届いていないことを示さない。

### 操作の表し方

操作は、読み直した状態へ再適用できる形で表す。操作ごとの入力と適用の規則は `docs/operations.md` にある。

### オフラインのとき

アプリ（Android とデスクトップ）は、S3 につながらないあいだの項目の削除だけを端末に溜め、つながったら 1 回の書き込みにまとめて適用する。
削除は再適用してもほかの端末の変更と衝突しない（対象がもう無ければ何もしない）。それ以外の操作（フォルダの削除・移動・名前の変更、
項目の移動など）は、つながっているときだけ受け付け、つながらなければ失敗として利用者に伝える。Native Messaging のホストは溜めない。

- **溜めるのは、S3 につながらないために書けなかった削除。** 通信の失敗と、結果が不明（「応答ごとの扱い」）のまま終わった書き込みが当たる。
  確かめられなかった書き込み（「成功の判定」）も、終わったときの失敗が結果の不明なものなら溜める。書き換えが済んでいれば、
  あとで適用するときには対象がもう無いので、何もしない。権限が無い・データが壊れている・形式が新しい、などの失敗では溜めず、
  失敗として利用者に伝える
- **溜めた削除は、接続先ごとに端末のファイルに持つ。** 対象（フォルダの ID と項目の ID の組）の並びを、バケットとプレフィックスごとの
  ファイルに書き、次の起動でも読む。ファイルを読めないか壊れていれば、溜めた削除は無いものとする。接続先を変えたら、
  前の接続先のローカルキャッシュを消すのと一緒に、前の接続先の溜めた削除も捨てる
- **溜めた削除の項目は、消したものとして見せる。** 読んであるマニフェストと項目の上に重ね、リストとフォルダの件数から除く。
  溜めた削除があるあいだは、メインの画面の帯に「削除した n 件の項目は、まだ保存先に反映していません。ネットワークにつながったら反映します。」
  と出す（n は溜めた項目の数）。削除して溜めたときは、ふつうに削除したときのお知らせの代わりに
  「n 件の項目を削除しました。ネットワークにつながったら保存先に反映します。」を「元に戻す」付きで出す。「元に戻す」を押したら、
  その回に溜めた削除を溜めた削除から外し、項目を見せ直す（S3 には書かない）。結果が不明のまま溜めた削除が、実際には S3 に届いていた
  場合も、元に戻すときは S3 に書かないので、次に読み直すとその項目は消えている
- **適用するのは、起動したとき、設定を保存したとき、読み直したとき、ほかの操作を書く前（以前の状態に戻す前を含む）。** 起動・設定の保存・読み直しでは、
  マニフェストを読み書きできるものとして読めたあとに適用する。読み直すのは、読み直すボタンを押したとき、ほかのプロセスが S3 へ書いたことを
  知ったとき（デスクトップ）、画面が前面に戻ったときとネットワークにつながったとき（Android）。デスクトップはネットワークの復帰を見張らない。
  ほかの操作を書く前には、先に溜めた削除を適用し、適用できなければその操作は書かず、書けなかったものとして利用者に伝える。
  項目の削除なら、つながらないための失敗のときは、その削除も溜める
- **溜めた削除は、すべてまとめて 1 回の書き込みにする。** 書き込みの手順も再適用の規則もほかの操作と同じで、もう無い対象は何もしない
  （`docs/operations.md` の「項目の削除」）。書けたら溜めた削除を空にし、ファイルを消す。S3 につながらなければ溜めたまま次の機会を待ち、
  帯のほかに失敗は伝えない。ほかの失敗なら溜めたまま、失敗として利用者に伝える

### マニフェストを新しく作る

マニフェストを新しく作るのは、初期設定と既存の cloud-marks からの移行という、利用者が明示した操作のときだけとする。
新しく作るマニフェストは、ヘッダーとルートフォルダを持つ。`If-None-Match: *` を付けて PUT する。`409` のときと結果が不明のときは、
同じ PUT を再送する。`412` ならマニフェストを 1 回読み、`commit` が自分の振ったものなら作れていた。そうでなければ既にあるので作らない。

マニフェストの GET が `404` を返しても、そのことだけを理由にマニフェストを作らない。ローカルキャッシュにマニフェストがあるのに
`404` が返ったら、失敗として利用者に伝える。

## キャッシュ

- マニフェストは ETag と一緒にローカルキャッシュに持ち、手順 1 の条件付きの GET に使う
- 項目ファイルは書き換えないため、キーごとにローカルキャッシュに持てば古くならない
- 新しいマニフェストをローカルキャッシュに持ったら、そのマニフェストが指さない項目ファイルをローカルキャッシュから消す
- ローカルキャッシュのマニフェストや項目ファイルが検証に通らなければ、ローカルキャッシュを丸ごと消し、何も無い状態から S3 を読み直す
- いまのマニフェストが指す項目ファイルが `404` を返したら、マニフェストを一度だけ読み直す。読み直したマニフェストがまだ同じファイルを
  指していれば、そのフォルダは壊れているとみなし、「項目ファイル」の「読み手が確かめること」と同じく扱う

## 古いファイルの削除

マニフェストから参照されなくなった項目ファイルは、デスクトップのアプリが消す。Android と Native Messaging のホストは消さない。
間隔は 1 日に 1 回程度とする。

1. マニフェストを GET する（ローカルキャッシュは使わない）。**`200` が返り、検証に通り、`version` が自分の知っているバージョン以下のときだけ続ける。**
   それ以外は何も消さない
2. `<プレフィックス>/folders/` を ListObjectsV2 で一覧する。**ページングで最後まで読む**
3. 次のすべてを満たすキーを消す
   - `folders/<UUID>/<UUID>.jsonl.gz` の形に厳密に合う（合わないキーには触らない）
   - マニフェストのどのフォルダの `<id>/<items>` の組とも一致しない（ファイルの ID だけで比べない）
   - 最終更新から 24 時間を過ぎている。経過は、一覧の応答の `Date` と各キーの `LastModified` の差で測る（端末の時計は使わない）。
     一覧が複数ページにわたるときは、最初のページの応答の `Date` を使う

- 24 時間の猶予は、書き込みの手順 3 で置いてから手順 4 でマニフェストを書き換えるまでのあいだのファイルを消さないため。
  手順 3 から手順 4 までは 1 時間を超えないので、猶予はそれより十分に長い
- 書き込みが成功するのは、最新のマニフェストに対する `If-Match` の条件を満たしたときだけ。そのため、書き込みの手順 3 で
  新しく置いたものを除けば、いま参照されていないファイルが、あとからマニフェストに参照されることはない
- 古いマニフェストを持ったままの読み手が、消えたファイルを読もうとして `404` を受けたら、マニフェストから読み直す

### バージョニングとの関係

バケットのバージョニングを有効にしていると、マニフェストの書き換えと古いファイルの削除のたびに、S3 のオブジェクトの古いバージョンと
削除マーカーが残る。プレフィックスにライフサイクルルールを付けて消す。

- `NoncurrentVersionExpiration`（たとえば 30 日）で古いバージョンを消す
- `Expiration` の `ExpiredObjectDeleteMarker: true` で、古いバージョンが無くなった削除マーカーを消す。
  `Expiration` に `Days` は付けない（いまのマニフェストまで消えるため）

#### 以前の状態に戻す

古いバージョンを消すまでの期間の中なら、マニフェストの古いバージョンと、それが指していた項目ファイルの古いバージョンを組み合わせて、
過去の状態に戻せる。アプリ（Android とデスクトップ）は、利用者が選んだ時点の状態に、次の手順で戻す。Native Messaging のホストは戻さない。

1. マニフェストのキーを ListObjectVersions で一覧する。ページングで最後まで読み、キーが一致するものだけを残す。
   削除マーカーといまのバージョンを除いた残りが、戻せる時点になる
2. 利用者が選んだ時点のマニフェストを、versionId を付けて GET する。「読み手が確かめること」と同じ検証をし、通らなければ戻さない。
   `readableBy` か `version` が自分の知っているバージョンより新しいときも戻さない
3. 書き込みの手順で、1 回の書き込みとして書く。書き込みの手順 2 に当たる規則は次のとおり
   - 戻す時点のマニフェストのフォルダの並びを、書く中身にする。マニフェストのヘッダーの `version` と `readableBy` は、戻す時点のものを書く
   - 項目ファイルは、いまのマニフェストが同じフォルダで同じファイルを指していればそのまま使う。指していなければ、
     戻す時点のファイルの中身を、新しいファイルの ID で置く
   - 戻す時点のファイルの中身は、そのキーを GET して得る。`404` か `403` なら、そのキーのバージョンのうち、削除マーカーでない
     最も新しいものを、versionId を付けて GET する。得た中身は「項目ファイル」の「読み手が確かめること」で確かめる
   - 置くファイルの中身をすべて得て確かめてから、書き込みの手順 3 の PUT を始める。得られないものや検証に通らないものがあれば、何も PUT せずに戻さない
   - `412` などで再適用するときは、読み直したいまのマニフェストと比べ直す。そのあいだにほかの端末が書いた変更も取り消される
4. 確かめられなかったとき（「成功の判定」）は、書き直さずに利用者に伝える。書き直すと、届いていた場合にすべてのフォルダのファイルを置き直すことになるため

- 削除マーカーは外さない。もとのキーのファイルをふたたび参照すると、参照されていないあいだに古いファイルの削除で消されることがある。
  新しいファイルの ID で置けば、置いたファイルは最終更新からの 24 時間の猶予で守られるので、古いファイルの削除を止めなくてよい
- 溜めた削除があれば、先に書く（「オフラインのとき」）
- いまのマニフェストが壊れているときは、アプリからは戻せない。手で戻すときは、デスクトップのアプリをすべて終了して古いファイルの削除を止めてから、
  戻すマニフェストが指すファイルのうち消えているものを古いバージョンから戻し、マニフェストを戻す。消えているファイルは、
  同じキーへコピーするか、削除マーカーを外して戻す
- 古いバージョンを何日残すかは、利用者が決める。アプリはその日数に頼らない。プレフィックス全体に同じ日数のルールを付けると、
  残っているマニフェストのバージョンが指すファイルのバージョンも残る。ファイルが古いバージョンになるのは、それを指すマニフェストが
  古いバージョンになったあとだから

## 権限

クライアントごとに要る S3 の権限は次のとおり。いずれも対象のバケットとプレフィックスに限る。

| 操作 | `s3:GetObject` | `s3:PutObject` | `s3:ListBucket` | `s3:DeleteObject` | `s3:ListBucketVersions` | `s3:GetObjectVersion` |
|---|---|---|---|---|---|---|
| 読み書き（Android・デスクトップ・ホスト） | 要る | 要る | 推奨 | 要らない | 要らない | 要らない |
| 古いファイルの削除（デスクトップ） | 要る | 要らない | 要る | 要る | 要らない | 要らない |
| 以前の状態に戻す（Android・デスクトップ） | 要る | 要る | 推奨 | 要らない | 要る | 要る |

- `If-Match` を付けた PUT には、`s3:PutObject` に加えて `s3:GetObject` が要る
- `s3:ListBucket` が無いと、存在しないオブジェクトの GET は `404` ではなく `403` を返す。読み書きのクライアントにも与えておくと、
  「無い」と「権限が無い」を見分けられる。`s3:ListBucket` はバケットに対する権限で、プレフィックスへは `s3:prefix` の条件で絞る
- 書き込みの手順は、`404` と `403` を見分けられなくても誤らない。どちらも失敗として伝え、マニフェストを勝手に作らない
- `s3:ListBucketVersions` は `s3:ListBucket` と同じくバケットに対する権限で、プレフィックスへは `s3:prefix` の条件で絞る。
  以前の状態に戻すときも、削除マーカーを外す `s3:DeleteObjectVersion` は使わない
- 暗号化に SSE-KMS を使うなら、`kms:GenerateDataKey` と `kms:Decrypt` も要る
- 接続の確認に `ListBuckets` を使わない。マニフェストの GET で確かめる
