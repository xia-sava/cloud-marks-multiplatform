# S3 上の形式

Cloud Marks のデータは S3 の 1 つのプレフィックスの下に置く。Android・デスクトップ・Native Messaging のホストは
対等にこれを読み書きし、中継するサーバーは置かない。

対象は AWS の S3 と、PutObject の `If-Match` / `If-None-Match` に対応する互換のストレージに限る。

## 構成

データは、フォルダの木を持つ**目録**と、フォルダごとの項目を持つ**フォルダのファイル**からなる。

```text
<プレフィックス>/
├─ manifest.jsonl.gz                          目録
└─ folders/<フォルダの ID>/<ファイルの ID>.jsonl.gz   フォルダのファイル
```

- 書き換えるオブジェクトは目録だけ。フォルダのファイルは一度置いたら書き換えない。フォルダの中身が変わるときは、
  新しいファイルの ID で別のオブジェクトとして置き、目録が指す先を替える
- 目録の書き換えは条件付き書き込み（`If-Match`）で行う。目録の中身がそのまま全体の状態になり、
  何フォルダにまたがる変更も、目録の書き換え 1 回で一度に反映される
- バケットとプレフィックスは利用者が設定で与える。プレフィックスは前後の `/` を除いて扱い、キーは
  `<プレフィックス>/manifest.jsonl.gz` のように `/` でつなぐ。プレフィックスが空なら、キーは `manifest.jsonl.gz` から始まる

## 共通の決まり

- **JSONL。** 1 行に 1 つの JSON オブジェクトを書き、各行を LF で終える。最後の行も LF で終える。空の行は置かない。
  文字コードは BOM の無い UTF-8
- **1 行目は見出し。** 2 行目から中身が続く
- **gzip で圧縮して置く。** キーの末尾は `.jsonl.gz`、`Content-Type` は `application/gzip`。
  `Content-Encoding` は付けず、読み手が自分で展開する（HTTP の層が展開して、長さや ETag の扱いが揃わなくなるのを避けるため）
- **ID は乱数の UUID（版 4）。** RFC 9562 の小文字・ハイフン区切りの 36 文字（例：`0b9a6c1e-3f2d-4e5a-9b7c-1d2e3f4a5b6c`）。
  フォルダ・項目・フォルダのファイル・書き込みのそれぞれに振る。比べるときは文字列として比べる。
  ID はキーの一部になるため、この形（小文字の 16 進で 8-4-4-4-12）に合わない値は壊れているとみなす。読み手は版の桁を確かめない
- **日時は RFC 3339 の UTC。** 書き手は末尾を `Z` にし、小数部をちょうど 3 桁で書く（例：`2026-11-16T12:34:56.789Z`）。
  ミリ秒未満は切り捨てる。読み手は小数部の桁数によらず受け入れる
- **ETag は不透明な値として扱う。** 応答の値を引用符ごとそのまま覚えて条件に渡し、中身を解釈しない
  （暗号化の設定によっては中身の MD5 ではない）

## 形式の版

形式の版は目録の見出しだけが持ち、データ全体に効く。フォルダのファイルの形を変えるときも、目録の版を上げる。

- `version`：データを書いた形式の版
- `readableBy`：このデータを読むのに要る最低の版。`version` 以下

クライアントは、自分の知っている版を N として次のように振る舞う。

| 目録の見出し | 振る舞い |
|---|---|
| `readableBy` > N | 読まない。「アプリの更新が要る」と伝える |
| `readableBy` ≤ N < `version` | 読むだけにして、書かない。古いファイルの削除もしない。「アプリの更新が要る」と伝える |
| `version` ≤ N | 読み書きする |

- 書き手は、読んだ目録の `version` のまま書く。その版で表せない内容を書くときだけ `version` を上げる
- 欄を足す変更は、古いクライアントが知らない欄を落として書き戻さないよう、必ず `version` を上げる。
  古いクライアントが無視して読んでも誤らない欄なら `readableBy` は据え置き、誤るなら `readableBy` も上げる
- 新しい版で表す機能は、すべてのクライアントがその版を読めるようになってから使い始める
- 読み手は、自分の知っている版以下のすべての版を読める
- 読み手は見出しを `format`、`version` と `readableBy`、残りの欄の順に確かめる。版が自分より新しいときに
  ほかの検証で失敗したら、「壊れている」ではなく「アプリの更新が要る」と伝える
- 書き手は、ここに定めた欄だけを書く。読み手は、知らない欄があっても無視して読む

## 目録

キーは `<プレフィックス>/manifest.jsonl.gz`。

### 見出し（1 行目）

```json
{"format":"cloud-marks-manifest","version":1,"readableBy":1,"commit":"<UUID>","updatedAt":"2026-11-16T12:34:56.789Z","updatedBy":"desktop"}
```

| 欄 | 型 | 内容 |
|---|---|---|
| `format` | 文字列 | `"cloud-marks-manifest"` |
| `version` | 整数 | 形式の版。1 以上 |
| `readableBy` | 整数 | 読むのに要る最低の版。1 以上で `version` 以下 |
| `commit` | 文字列 | 書き込みごとに新しく振る UUID。自分の書き込みが成功していたかを確かめるのに使う（「書き込みの手順」） |
| `updatedAt` | 文字列 | 書き込んだ日時 |
| `updatedBy` | 文字列 | 書き込んだクライアントの種類。`"android"`・`"desktop"`・`"host"` など。後から追うための記録で、読み手は知らない値も受け入れ、この値で振る舞いを変えない |

### フォルダ（2 行目から）

1 行に 1 フォルダ。**2 行目は必ず根のフォルダ**で、`parent` が null なのはこの行だけ。根は名前が空で、画面には名前を出さない。
根もほかのフォルダと同じく、子のフォルダと項目を持てる。

```json
{"id":"<フォルダの ID>","parent":"<親のフォルダの ID>","name":"資料","items":"<ファイルの ID>","count":3}
```

| 欄 | 型 | 内容 |
|---|---|---|
| `id` | 文字列 | フォルダの ID |
| `parent` | 文字列か null | 親のフォルダの ID。根だけが null |
| `name` | 文字列 | フォルダの名前。根は空、それ以外は空でない。`/` を含め、どの文字でも使える。兄弟で同じ名前があってもよい |
| `items` | 文字列か null | このフォルダの項目を持つフォルダのファイルの ID。項目が無ければ null |
| `count` | 整数 | 項目の数。0 以上。項目が無ければ 0 |

- **並びは、根から深さ優先の行きがけ順。** 親は必ず子より前の行に出てくる。兄弟どうしの並び順は、そのまま行の順になる
- フォルダは、子のフォルダと項目の両方を持てる。表示の並びは子のフォルダが先、項目が後で、
  子のフォルダの並びは目録が、項目の並びはフォルダのファイルが持つ
- `items` が null であることと `count` が 0 であることは、必ず揃う。書き手は、項目の無いフォルダのファイルを置かない

### 読み手が確かめること

次のどれかを満たさない目録は壊れているとみなす。読み手は失敗として利用者に伝え、書き込みも古いファイルの削除もしない。
壊れた目録は、バケットのバージョニングで残っている古い版から手で戻す。

- gzip として展開でき、BOM の無い UTF-8 として読め、すべての行が JSON のオブジェクトとして読める。空の行が無く、最後の行が LF で終わる
- 1 行目が見出しで、`format` が `"cloud-marks-manifest"` であり、見出しとフォルダの各行が、表の欄をすべて表の型で持つ。
  null を許す欄も、欄ごと省くことはできない。整数は JSON の整数の字句で書かれている。日時は RFC 3339 の日時として読める
- `version` と `readableBy` が 1 以上の整数で、`readableBy` が `version` 以下である
- `commit`・`id`・`parent`・`items` の値が、null を許すものを除いて UUID の形である
- `id` が重複しない
- 2 行目があり、その `parent` が null で `name` が空である（根）
- 3 行目からの各行の `parent` が、**直前の行から `parent` を辿って根へ向かう途中にあるフォルダ**（直前の行そのものを含む）の `id` である。
  これで、親が先にあること、循環が無いこと、行きがけ順であることを 1 回の走査で確かめられる
- 3 行目からの各行の `name` が空でない。`count` が 0 以上の整数である
- `items` が null であることと `count` が 0 であることが揃っている

## フォルダのファイル

キーは `<プレフィックス>/folders/<フォルダの ID>/<ファイルの ID>.jsonl.gz`。

### 見出し（1 行目）

```json
{"format":"cloud-marks-items","folder":"<フォルダの ID>"}
```

| 欄 | 型 | 内容 |
|---|---|---|
| `format` | 文字列 | `"cloud-marks-items"` |
| `folder` | 文字列 | このファイルを持つフォルダの ID。キーのフォルダの ID と同じ |

形式の版は目録の見出しが持つため、フォルダのファイルは版を持たない。

### 項目（2 行目から）

1 行に 1 項目。行の順が表示の並び順になる。

```json
{"id":"<項目の ID>","url":"https://example.com/","title":"Example","added":"2026-11-16T12:34:56.789Z"}
```

| 欄 | 型 | 内容 |
|---|---|---|
| `id` | 文字列 | 項目の ID。すべてのフォルダを通して重複しない |
| `url` | 文字列 | 空でない。スキームは問わない（`https`・`http` のほか `about:` や `moz-extension:` もありうる） |
| `title` | 文字列 | 空でもよい |
| `added` | 文字列 | 省略可。追加した日時。既存の cloud-marks から取り込んだ項目には無い |

- 同じ URL の項目が複数あってもよい
- 既読の印は持たない。フォルダに残っている項目が未読で、読み終えた項目は利用者が消す

### 読み手が確かめること

次のどれかを満たさないファイルは壊れているとみなす。

- gzip として展開でき、BOM の無い UTF-8 として読め、すべての行が JSON のオブジェクトとして読める。空の行が無く、最後の行が LF で終わる
- 見出しと項目の各行が、表の欄を表の型で持つ（`added` は省略可。持つなら RFC 3339 の日時として読める）
- 1 行目が見出しで、`format` が `"cloud-marks-items"` である
- `folder` が、キーのフォルダの ID とも、このファイルを指している目録のフォルダの `id` とも一致する
- 項目の行の数が、目録のそのフォルダの `count` と一致する
- `id` が UUID の形で、ファイルの中で重複しない。`url` が空でない

壊れたファイルを持つフォルダについては、その中身を変える操作を止め、利用者に伝える。そのフォルダごとの削除や、
ほかのフォルダへの操作はできる。

## 書き込みの手順

すべての変更は、次の手順を 1 回の書き込みとして行う。

1. 目録を読む。手元に目録と ETag があれば `If-None-Match: <ETag>` を付けて GET し、`304` なら手元のものを使う。
   `200` と `304` 以外は失敗として利用者に伝える（「目録を新しく作る」）。読んだ目録は検証し、版を確かめる（「形式の版」）
2. 操作を、読んだ状態に適用する。適用した結果が読んだ状態と同じなら、ここで終える（PUT しない）
3. 中身の変わったフォルダごとに、新しいファイルの ID でフォルダのファイルを PUT する。`If-None-Match: *` を付ける。
   項目が無くなったフォルダはファイルを置かず、`items` を null にする。
   複数のファイルは並べて送ってよく、すべて成功してから手順 4 へ進む
4. 見出しの `commit` に新しい UUID を振り、`If-Match: <手順 1 の ETag>` を付けて目録を PUT する。
   **手順 3 の最初の PUT から 1 時間を過ぎていたら、手順 4 を送らずに手順 1 からやり直す**（ファイルも新しい ID で置き直す）。
   経過は端末の単調な時計で測る
5. 応答に応じて次のようにする

### 応答ごとの扱い

手順 4（目録の PUT）：

| 応答 | 扱い |
|---|---|
| `200` | 成功。応答の ETag と書いた目録を手元に持つ |
| `412` | 読み直して、「成功の判定」をする。成功していなければ、手順 1 から操作を適用し直す |
| `409` | 同時に走った書き込みとの衝突。同じ PUT を送り直す |
| `404` | 目録が消されている。失敗として利用者に伝え、書き込みを止める |
| 結果が分からない（タイムアウト、接続の切断、`5xx`、`503 SlowDown`） | 読み直して、「成功の判定」をする。成功していなければ、手順 1 から操作を適用し直す |
| `403` など、上のどれでもないもの | 失敗として利用者に伝え、適用し直さない |

手順 3（フォルダのファイルの PUT）：

| 応答 | 扱い |
|---|---|
| `200` | 成功 |
| `409` または結果が分からない | 同じ PUT を送り直す |
| `412` | 送り直したあとなら、先の PUT が成功していた。最初の PUT で返ったなら、ファイルの ID を振り直して置き直す |
| `403` など、上のどれでもないもの | 失敗として利用者に伝え、適用し直さない |

- 送り直しと適用し直しには、間を空けて回数に上限を設ける。上限を超えたら失敗として利用者に伝える
- 手順 4 の PUT を一度でも送ったあとの目録の GET（成功の判定のための読み直し、適用し直しの手順 1）は、
  結果が分からないときに送り直す。手順 4 より前の GET は送り直さない

### 成功の判定

自分の目録の PUT が、応答を受け取れないまま成功していることがある（応答が途中で切れた、遅れて届いた、
SDK が自動で送り直して `412` を受けた、など）。このまま操作を適用し直すと、追加のような操作では項目が二重になる。
これを次の二つで防ぐ。

- **1 回の操作のあいだに手順 4 で振った `commit` をすべて覚えておく。** 読み直した目録の `commit` がそのどれかなら、
  書き込みは成功していた
- **操作が作るもの（フォルダ・項目）の ID は、操作を組み立てるときに一度だけ振り、適用し直すときに振り直さない。**
  適用し直すとき、その ID が既にあれば、その部分は適用済みとして扱う。自分の書き込みのあとに別の端末の書き込みが挟まって
  `commit` が替わっていても、これで二重にならない

`412` か結果が分からない応答を受けた手順 4 の PUT は、届いたかどうかが分からないものとして記録する。読み直した目録の
`commit` が自分の振ったものでなく、ETag がその PUT の `If-Match` と違えば、その PUT はもう届かないとして記録を消す。

記録が残ったまま書き込みを終える（読み直しが上限まで失敗した、など）ときは、ただの失敗ではなく
**確かめられなかった**として返す。書き換えが済んでいることもある。呼び出し側は、同じ操作（同じ ID）でもう一度
書き込めば、届いていた分は適用済みになり二重にならない。やり直した書き込みが成功以外で終わっても、確かめられないままとして扱う
（やり直しの失敗は、先の PUT が届いていないことを示さない）。

### 操作の表し方

操作は、読み直した状態へ適用し直せる形で表す。操作ごとの入力と適用の規則は `docs/operations.md` にある。

### オフラインのとき

Android は、つながらないあいだの項目の削除だけを手元に溜め、つながったら 1 回の書き込みにまとめて適用する。
削除は適用し直してもほかの端末の変更とぶつからない（対象がもう無ければ何もしない）。それ以外の操作は、つながっているときだけ受け付ける。

### 目録を新しく作る

目録を新しく作るのは、利用者が明示した操作（初期設定、既存の cloud-marks からの移行）のときだけとする。
新しく作る目録は、見出しと根のフォルダを持つ。`If-None-Match: *` を付けて PUT する。`409` と結果が分からないときは同じ PUT を
送り直す。`412` なら目録を 1 回読み、`commit` が自分の振ったものなら作れていた。そうでなければ既にあるので作らない。

目録の GET が `404` を返しても、そのことだけを理由に目録を作らない。手元に目録のキャッシュがあるのに `404` が返ったら、
失敗として利用者に伝える。

## キャッシュ

- 目録は ETag と一緒に手元に持ち、手順 1 の条件付きの GET に使う
- フォルダのファイルは書き換えないため、キーごとに手元に持てば古くならない
- 新しい目録を手元に持ったら、その目録が指さないフォルダのファイルを手元から消す
- 手元の目録やフォルダのファイルが検証に通らなければ、手元のキャッシュを丸ごと消し、手元に何も無いものとして S3 から読み直す
- いまの目録が指すフォルダのファイルが `404` を返したら、目録を一度だけ読み直す。読み直した目録がまだ同じファイルを指していれば、
  そのフォルダは壊れているとみなす（「フォルダのファイル」の「読み手が確かめること」と同じく扱う）

## 古いファイルの削除

目録から参照されなくなったフォルダのファイルは、デスクトップのアプリが消す。Android と Native Messaging のホストは消さない。
間隔は 1 日に 1 回程度とする。

1. 目録を GET する（手元のキャッシュは使わない）。**`200` が返り、検証に通り、`version` が自分の知っている版以下のときだけ続ける。**
   それ以外は何も消さない
2. `<プレフィックス>/folders/` を ListObjectsV2 で一覧する。**ページングで最後まで読む**
3. 次のすべてを満たすキーを消す
   - `folders/<UUID>/<UUID>.jsonl.gz` の形に厳密に合う（合わないキーには触らない）
   - 目録のどのフォルダの `<id>/<items>` の組とも一致しない（ファイルの ID だけで比べない）
   - 最終更新から 24 時間を過ぎている。経過は、一覧の応答の `Date` と各キーの `LastModified` の差で測る（端末の時計は使わない）。
     一覧が複数ページにわたるときは、最初のページの応答の `Date` を使う

- 24 時間の猶予は、書き込みの手順 3 で置いてから手順 4 で目録を書き換えるまでのあいだのファイルを消さないため。
  手順 3 から手順 4 までは 1 時間を超えないので、猶予はそれより十分に長い
- 書き込みは必ず最新の目録に対する `If-Match` を通る。そのため、書き込みの手順 3 で新しく置いたものを除けば、
  いま参照されていないファイルが、あとから目録に参照されることはない
- 古い目録を持ったままの読み手が、消えたファイルを読もうとして `404` を受けたら、目録から読み直す

### バージョニングとの関係

バケットのバージョニングを有効にしていると、目録の書き換えと古いファイルの削除のたびに、S3 のオブジェクトの古い版と
削除マーカーが残る。プレフィックスにライフサイクルの規則を付けて消す。

- `NoncurrentVersionExpiration`（たとえば 30 日）で古い版を消す
- `Expiration` の `ExpiredObjectDeleteMarker: true` で、古い版が無くなった削除マーカーを消す。
  `Expiration` に `Days` は付けない（いまの目録まで消えるため）

古い版を消すまでの期間の中なら、目録の古い版と、その目録が指していたファイルの古い版を組み合わせて、過去の状態へ戻せる。
戻すときは、古いファイルの削除を止め、戻す目録が指すファイルの削除マーカーを外してから、目録を戻す。
戻した目録は、参照されていなかった古いファイルをふたたび参照するため、この順を守らないとそれらが消される。

## 権限

クライアントごとに要る S3 の権限は次のとおり。いずれも対象のバケットとプレフィックスに限る。

| 操作 | `s3:GetObject` | `s3:PutObject` | `s3:ListBucket` | `s3:DeleteObject` |
|---|---|---|---|---|
| 読み書き（Android・デスクトップ・ホスト） | 要る | 要る | 推奨 | 要らない |
| 古いファイルの削除（デスクトップ） | 要る | 要らない | 要る | 要る |

- `If-Match` を付けた PUT には、`s3:PutObject` に加えて `s3:GetObject` が要る
- `s3:ListBucket` が無いと、無いオブジェクトの GET は `404` ではなく `403` を返す。読み書きのクライアントにも与えておくと、
  「無い」と「権限が無い」を見分けられる。`s3:ListBucket` はバケットに対する権限で、プレフィックスへは `s3:prefix` の条件で絞る
- 書き込みの手順は、`404` と `403` を見分けられなくても誤らない（どちらも失敗として伝え、目録を勝手に作らない）
- 暗号化に SSE-KMS を使うなら、`kms:GenerateDataKey` と `kms:Decrypt` も要る
- 接続の確認に `ListBuckets` を使わない。目録の GET で確かめる
